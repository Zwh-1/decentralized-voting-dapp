## 1. 用途与它不能替代什么

本文件按规格 §13.1 的 **11 项验收清单**逐项给出「验收项 / 命令 / 实测输出 / 结论」。它是**证据**，不是权威；权威是 `adr/` 下的已接受 ADR 与 `specs/` 下的设计规格。

**这一轮必须先说清楚一条边界，否则下面每张表都会被误读：本阶段的 Docker 从未跑起来过。**

根因已在计划 §14.1 实测记录：Windows 可选功能 `VirtualMachinePlatform` 未启用（连 `Get-WindowsOptionalFeature` 查询都要求提权），因此 WSL2 无法创建虚拟机，Docker Desktop 的 WSL2 后端也就无法启动引擎。`docker version` 报 `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`。解除需要管理员提权**并重启**，使用者已决定暂缓。**审批提示在本会话被禁用**，所以这不是一个可以自行绕过的问题。

由此得出的四条硬结论，贯穿全文：

1. **镜像从未构建**（`docker build` 没跑过），因此规格 §13.1 第 2 项（镜像体积）、以及任何依赖镜像存在的项，都是 **未实测**。
2. **容器从未启动**（`docker compose up` 没跑过），因此 `docker compose ps` 全 healthy、schema 幂等、监控栈、告警投递全部是 **未实测**。
3. **「配置写好了」不等于「已验证」。** 本文件把「文件存在且能被真实工具解析」与「运行时行为已观察」严格分成两类；只有后者才写「已实测」。
4. **桩化验证证明的是脚本在该停的地方停住了，不是容器能用。** `ops/deploy/selftest.sh` 的原文件头就把这条写死了，本文件沿用同一措辞。

**因此本阶段真正的交付物不是「跑起来的部署」，而是「一套在容器可用之前就能证伪自己的部署逻辑」，以及一份如实标注边界的记录。** 后者不是退让：一个把「配置已就绪」写成「已验证」的基线记录，比没有基线记录更糟。

### 2.3 验收项 3：`mysql2` 进入 standalone 输出

| 项       | 内容                                                                                                                                                                                                                                                      |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 验收项   | `.next/standalone/node_modules/mysql2` 存在                                                                                                                                                                                                               |
| 命令     | `node -e "console.log(require.resolve('mysql2/promise'))"`（在 standalone 副本内执行）                                                                                                                                                                    |
| 实测输出 | **否定的**：`standalone/node_modules/.pnpm/…/mysql2` **存在**（92 文件 / 0.53 MB），但**顶层链接不存在**；`standalone/web/node_modules/next` 是指回仓库绝对路径的 Junction。副本移到仓库外后 `require.resolve("mysql2/promise")` → **`MODULE_NOT_FOUND`** |
| 结论     | **部分实测，且结果是「本机产出的 standalone 不自包含」**——这一项按原验收标准**不成立**                                                                                                                                                                    |
| 证伪方式 | 移除 `serverExternalPackages` → 应改变输出。**未做**                                                                                                                                                                                                      |

这条要分清两件事，混起来就会得出错误结论：

- **文件确实被追踪进来了**。`mysql2` 的 92 个文件在 `standalone/node_modules/.pnpm/` 下，说明 Next 的依赖追踪路径是真实的（只是 `mysql2/index.js` 不在集合内，那是**正常**的：应用只 `import "mysql2/promise"`，而 `promise.js` 不 require `index.js`）。
- **缺的是链接，不是文件**。在仓库内它能跑，是因为 Node 沿目录向上逃逸到**仓库根**的 `node_modules`（§14.7 实测：解析到 `D:\桌面\实习项目\…\node_modules\.pnpm\mysql2@3.24.4_…`）。镜像里代码放到 `/app` 之后，向上走 `/app/node_modules`、`/node_modules` 都不存在，**运行时才会** `MODULE_NOT_FOUND`。
- 对照：同一副本里 `require.resolve("next")` 成功，但只因那个 Junction 指回了本机仓库——**容器内会悬空**。

因此 `web/Dockerfile` 已加构建期自检 `RUN node -e "require.resolve('mysql2/promise')"`，让不自包含的镜像在**构建时**失败而不是运行时才崩；runner 阶段也从 `runtime-deps`（`pnpm install --frozen-lockfile --prod`）复制 pnpm 自己产生的**相对符号链接树**，而不是依赖 standalone 的追踪结果。**这两处修正本身都没有被镜像构建验证过**——它们是针对已实测缺陷的处置，不是已验证的修复。

**Linux 上是否会同样失败：未实测。** pnpm 在 Linux 用真实符号链接而非绝对路径 junction，Next 的追踪器在那边大概率能建出完整链接。这是推断，不是观察。

### 2.4 验收项 4：零停机发布

| 项       | 内容                                                                                                            |
| -------- | --------------------------------------------------------------------------------------------------------------- |
| 验收项   | 发布期间持续探测 `/api/health` 的时间序列，**失败请求数为 0**                                                   |
| 命令     | `./ops/deploy/probe-loop.sh https://<域名>/api/health 120 2 &` 与 `<server>: ./ops/deploy/deploy.sh <sha>` 并行 |
| 实测输出 | **未实测：实验组与对照组都没有做。** 没有服务器、没有域名、没有 TLS、没有镜像。                                 |
| 结论     | **未实测**                                                                                                      |
| 证伪方式 | 改用原地 `up -d` 重跑同一探测 → 应出现失败请求。**未做**（对照组未做）                                          |

**唯一已实测的部分是「仪器本身能看见失败」**——这一点不是形式主义，因为 runbook 明写「一个报告 0 失败的实验组，只有在同一台仪器能探测到已知存在的失败时才有意义」。`ops/deploy/probe-loop.sh` 打一个**真实 HTTP 服务器**：

| 场景   | 实测输出                                                                      | 退出码 |
| ------ | ----------------------------------------------------------------------------- | ------ |
| 全成功 | `{"total":5,"succeeded":5,"failed":0,"maxConsecutiveFailures":0}`             | **0**  |
| 全失败 | `{"total":3,"failed":3,"maxConsecutiveFailures":3,"firstFailureAtSeconds":0}` | **1**  |

也就是说：探测循环能数失败、能数**连续**失败（用来区分一次掉连接与一段真实不可用窗口），并且失败会让退出码非零——`deploy.sh` 把非零退出当作发布失败，所以观察窗是**门**而不是报告。

**但「发布期间失败请求数为 0」这句话本阶段不能写。** 仪器可用 ≠ 被测量的那个窗口没出问题。

| 结论     | **未实测**                                                                                                          |
| 证伪方式 | 回滚后 `active-slot` 与 `previous-tag` 必须与发布前一致。**部分**：桩化自测覆盖了状态文件的写入值，但没有真实主机。 |

桩化替代（已实测）：`ops/deploy/selftest.sh` 的 case 4–7 断言了回滚的**顺序性质**——

- 回滚到仍在运行的槽位时**不重启任何容器**（快路径只改上游文件并 reload）；
- 回滚到冷槽时**先启动、先过健康门**；
- 回滚**拒绝**指向当前正在服务的那个 release；
- 上游渲染被拒时，**上一个上游文件被恢复**。

以及 case 1：`migrate` 失败时回滚路径**不跑迁移**，且输出明说 schema 未回滚。这些是「脚本在该停的地方停住」的证据，不是「回滚在一台真机器上花了几秒」的证据。

- shellcheck 与 `bash -n` 改为**遍历** `find ops -name '*.sh'` 而不是列举目录——将来新增目录也不会被遗漏；

- 新写的 `check-compose.py` 同时有入口（job `compose-isolation`）。

**证据只有在被自动执行时才是门禁**，否则它只是某一次的手工记录，下次改动照样能悄悄破坏它。

- 本文件的所有「已实测」都来自**宿主机**，没有一项来自容器内。容器内行为是本阶段最大的证据缺口。
- `docker compose config` 退出码 0 只证明 **YAML 与 compose schema 可解析**，不证明容器能起来。这是本文件反复强调的一条：**能被工具解析 ≠ 能运行**。
- 桩化自测（A-2/A-3）证明脚本在该停的地方停住了，**不**证明镜像可用、不证明部署在一台真机器上会成功。原文件头已把这条写死，本文件沿用同一措辞。
- Sepolia 的演示数据缺口（U-39/U-40）意味着**面试官现在打开页面会看到一片 `unknown` 加零个投票**。方案再完整也演示不出来——这条必须先清。
- 三处 Docker 之外的外部依赖（GitHub 仓库、服务器、SMTP）**同时**缺失，所以它们不是互相独立的三个缺口，而是「整条交付路径的运行时证据为零」这一个缺口。

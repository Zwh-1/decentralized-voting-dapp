## 2. 现状诊断

### 2.1 视觉层（批次 A）

当前为纯 Tailwind 工具类的极简拼装，问题具体为：

| 问题             | 证据                                                                                |
| ---------------- | ----------------------------------------------------------------------------------- |
| 无设计令牌       | 颜色散落为 `slate-500` / `rose-600` / `emerald-600` 等字面量，共 6 个组件各自硬编码 |
| 无视觉层次       | `PageShell` 仅标题 + 两行导航；页面无背景分区，所有卡片同权重                       |
| 状态色彩不成体系 | 「进行中 / 已结束 / 未开始」用文字而非色彩区分，一屏扫不出状态                      |
| 无加载骨架       | 读链期间显示「读取中…」文本，布局在数据到达时跳动                                   |
| 无空态设计       | 无投票时是一行灰字                                                                  |
| 无响应式         | `max-w-5xl` 固定单列，未针对移动端组织投票卡片                                      |

**约束**：批次 A 不得触碰任何业务逻辑。`PollBallot.tsx`（576 行）与 `PollAdmin.tsx`（754 行）承载已验证的禁用理由与写路径，其行为必须逐字保持不变——`ui:drill` 的断言是对着这些文本与属性写的。

### 2.2 现实机制（批次 B）

### 2.3 信任层（批次 C）

这是当前最实质的缺口。README 已诚实登记三条中心化风险，但**没有任何机制让第三方验证**：

| 风险                                           | 现状                                     | 后果                                         |
| ---------------------------------------------- | ---------------------------------------- | -------------------------------------------- |
| 发起人可任意增删白名单                         | 只有 `WhitelistUpdated` 事件，界面不展示 | 投票人无法知道规则是否被中途改动             |
| 发起人可在宽限期后 `sweepUnclaimed()` 取走押金 | 界面不提示剩余额度与时间                 | 投票人不知道自己的押金有被取走的风险         |
| 「投票结果」没有任何快照                       | 结果只在链上实时可读                     | 无法证明「某时刻的结果是这样」，事后不可举证 |

**批次 C 的合约改动方向**（待实现时细化）：

1. **规则承诺（commitment）**：`initialize` 时把 `(question, optionCIDs, endsAt, openToAll, creator)` 的哈希写入链上并公开。任何人都能据此重算并验证「规则自创建起未变」。
2. **`WhitelistUpdated` 的完整可审计性**：确保每次变更都带区块号，界面聚合成「规则变更史」。
3. **结果快照存证**：提供一个只读视图返回可哈希的结果摘要（各选项票数 + 阶段 + 结束时间），使第三方可以「链上读 → 本地哈希 → 与公示值比对」。
4. **押金风险公示**：界面明确显示宽限期截止时间与「若无人领取将被发起人取走」的金额。

**注意**：合约改动一律**不得削弱**已有安全属性。现有 157 个合约测试（含 1000 轮属性测试与四组重入矩阵）是底线，只能增不能减。

## 3. 执行顺序

按依赖关系排序，每批结束都必须全绿：

1. **批次 A**（无合约改动，风险最低，先交付可见成果）
2. **批次 B**（只读索引与前端，依赖 A 的视觉体系）
3. **批次 C**（合约改动 + 重新部署 + A/B 界面承接）

第 3 项需要重新部署，且会再次改变 ABI，因此放在最后——避免中途改 ABI 导致 A/B 返工。

## 5. 已知约束与陷阱

- **不得用 PowerShell 做文本替换**：本仓库此前发生过因此导致两个源文件损坏的事故（见上一份基线记录）。一律用 `edit` / `write` 工具。
- **`web/test/**` 无法导入 React/wagmi 组件**（`ERR_MODULE_NOT_FOUND`）。因此批次 A 中任何可测的逻辑（如状态 → 色彩令牌的映射、占比计算）必须放进 `web/src/lib/*` 纯函数。
- **`ui-drill.ts` 的 `READ_PAGE` 是模板字符串**：其中不能出现反引号，否则会截断。文件内已有注释警告。
- **视觉改动不得改变文本**：`ui:drill` 大量断言中文措辞（如「你当前投给了这个选项」「不在本投票的白名单里」）。改样式可以，改措辞会让 drill 失败——这是有意的耦合，措辞本身是被验证的行为。
- **`data.ts` 的索引器驱动部分不拆分**：上一轮已记录理由（与 `globalThis` 单例形成循环依赖）。

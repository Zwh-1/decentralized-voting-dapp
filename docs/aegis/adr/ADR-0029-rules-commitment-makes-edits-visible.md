# ADR-0029 — 规则承诺：让"规则有没有被改"成为可验证的事实

- 状态：已接受
- 日期：2026-09-21
- 相关：ADR-0001（链是唯一事实来源）、ADR-0017（比较同一瞬间）、ADR-0025（准入方式在 `initialize` 固定）、ADR-0026（每次对外写入都要有调用方或理由）

## 背景

这个投票合约在设计上把很多规则做成不可变的：`openToAll` 在 `initialize` 时固定且没有 setter（ADR-0025），选项在 `startPoll()` 之后冻结，发起人地址不可转移，`STAKE` 与 `REFUND_GRACE_PERIOD` 是常量。

但有两类内容**允许**在 `Phase.Setup` 阶段被发起人修改：

1. **选项**——可以 `addOption` / `removeOption` / `updateOption`；
2. **白名单**——可以 `setWhitelist` 反复增删。

这是有意的设计。发起人创建投票时通常还不知道最终选项、也还没收集到投票人地址，`Phase.Setup` 存在的意义就是让他们把这些准备好。所以"规则可以被改"本身不是缺陷。

缺陷在别处：**改过和没改过，从外部看起来一模一样**。

一个在投票开始后才看到这个页面的人，无法区分下面两种情况：

- 这个投票是「按创建时的样子开放投票的」；
- 这个投票是「创建后先被改过选项或白名单，再开放投票的」。

链上有 `OptionAdded` / `OptionRemoved` / `OptionUpdated` / `WhitelistUpdated` 事件，理论上可以自己把事件从头回溯一遍。但这要求读者：找到创建区块、按时间顺序拉全所有事件、自己重放一遍状态、还要处理 `updateOption` 这种"同一个选项被改过多次"的情况。**一个需要读者写脚本才能回答的问题，在实践中等于没有回答**——绝大多数人只会选择相信页面。

于是出现了一个信任缺口：页面声称的规则，和链上真实执行的规则，读者没有办法低成本地确认它们一致。

## 决策

在合约里增加一对值，构成一个**可自行比对的承诺**：

### 1. `rulesHash`——创建时的承诺

在 `initialize()` 里写入一次，**此后永不改动**：

```solidity
rulesHash = _rulesHash();
```

由于 `initialize` 执行时白名单必然为空、选项就是创建时传入的那批，因此这个值就是「**创建时规则**」的指纹。

### 2. `currentRulesHash()`——当前状态的重算

一个 `view` 函数，用**完全相同的方式**对**当前**链上状态重新计算一次指纹。

### 3. 指纹的内容

```solidity
keccak256(abi.encode(
    creator,        // 谁在管理
    question,       // 在问什么
    endsAt,         // 什么时候截止
    openToAll,      // 谁可以投票
    block.chainid,  // 哪条链
    address(this),  // 哪一个投票
    optionHashes,   // 选项：每个选项的 (id, labelCID)
    whitelistHashes // 白名单：已准入地址的排序列表
))
```

两者相同，说明这些内容自创建以来没有变过；不同，说明其中某一项被改过——**改动因此变得可检测**。

## 关键设计取舍

### 为什么是哈希，而不是把规则再存一份

规则本身在链上已经可读。再存一份副本既是冗余存储，又引入"副本与正本不一致"的新问题。指纹只需要能**区分不同**，不需要携带信息。

### 为什么用 `abi.encode` 而不是 `abi.encodePacked`

`encodePacked` 让相邻动态类型产生歧义：`("ab", "c")` 与 `("a", "bc")` 编码结果相同。那样两组真正不同的规则会撞到同一个哈希，承诺就形同虚设。`abi.encode` 为每个参数补齐边界，消除歧义。

### 为什么白名单要先排序

哈希不能依赖**添加顺序**。否则发起人把某个地址移除再加回来，白名单内容完全没变，哈希却变了，页面就会显示"规则被改动过"——一次纯粹的无意义告警。

**误报比漏报更能摧毁这个功能**：一旦用户发现"它老是乱报"，就会学会忽略这个提示，那么真正需要被看见的那次改动也会被一起忽略。`_whitelistHashes()` 因此对结果做插入排序。

### 为什么票数不在哈希范围内

投票不是规则。如果把票数计入，那么**每一个收到过票的投票都会显示"规则被改动过"**，包括完全正常的那些。承诺要覆盖的只是"读者被承诺了什么"，而票数是结果，不是承诺。

`test_RulesHash_IsUnchangedByVoting` 固定这一点。

### 为什么把 `address(this)` 放进哈希

否则两个规则完全相同的投票会得到同一个指纹，一个审查者可以把 A 投票的承诺复制到 B 投票上，比对依然通过——**承诺将可以被它本要审查的那一方伪造**。

`test_RulesHash_DiffersBetweenPollsWithIdenticalRules` 固定这一点。

### 为什么维护 `_whitelistKeys` 数组

`mapping` 无法遍历，而指纹必须能枚举白名单。因此在 `setWhitelist` 里用 `_whitelistKeyIndex` 记录每个地址**第一次**出现时的位置，只追加、从不删除。

不删除的原因：删除需要 swap-and-pop，会打乱数组顺序，而排序只是让"顺序不影响哈希"成立，数组本身的顺序稳定能让代码更容易推理。代价是每个不同地址多占一个 slot。

### 为什么 `currentRulesHash()` 是 view 而不是存下来的值

如果它也是一个创建时写入、从不更新的值，那么"自己和自己比对"什么也证明不了。**必须一侧是承诺、另一侧是现实**，比对才有意义。

### 被改过 ≠ 有问题

这是这个功能最容易被做错的地方。`Phase.Setup` 期间增删选项、维护白名单**本来就是正常流程**。因此：

- 合约不做任何拦截；
- 页面的措辞使用「规则在创建后有过改动」，并明确说明「这不一定有问题」；
- 单元测试 `rulesSummary` 断言这些措辞里**不出现**「篡改」「恶意」「作弊」「欺诈」等词。

读者被亏欠的是**知情**，不是判决。

### 未知状态不能被渲染成"没问题"

`rulesCheck` 有三个结果：`unchanged` / `changed` / `unknown`。

`unknown` 必须在**任意一侧读不到**时返回——包括读失败、返回空、返回零哈希。因为"读取失败所以显示规则完好"正是这个功能存在的意义所要消除的那种虚假保证。

零哈希被当作"不存在承诺"而非"匹配"：`0x00…0 === 0x00…0` 否则会给出一个自信的 `unchanged`，而那个承诺根本不存在。

### 为什么在浏览器里直接读链

`rulesHash` 和 `currentRulesHash()` 是两个合约调用，读者的浏览器可以**直接**向链发起。这一点在这里比其他任何地方都重要：**由"有可能改了规则的那一方"提供的"规则没有被改"徽章，价值为零**。这个面板的全部意义就是让读者不必相信这个页面。

两个读取放在**同一次批量请求**里，以保证它们描述**同一个区块**（ADR-0017）。分开读可能跨越区块边界，把承诺与另一个瞬间的状态相比，产生一个假阳性的 `changed`。

## 后果

### 正面

- 「规则是否被改过」从"需要写脚本回溯事件"变成"两次调用比一下"，任何人在区块浏览器上即可完成；
- 改动**可见**，页面不必再要求读者单方面信任；
- 误报被排序逻辑消除，"被改过"这个信号因此保持可信；
- 不改变任何投票行为，不引入新的写入路径，不扩大攻击面——纯读取。

### 负面

- `_whitelistKeys` 是新的存储，随不同地址数量线性增长（每个地址一个 slot + 一个 slot 的索引）；
- `currentRulesHash()` 是 O(n log n)，n 为白名单规模。它是 `view`，只在链下调用，不消耗交易 gas；但白名单极大时（本项目的种子数据是 200 个）读取会变慢；
- `rulesHash` 只覆盖**创建时**的规则。要判断"改了什么"，仍需回溯事件；这个功能回答的是"有没有改"，不是"改成了什么"。

### 中性

- 页面显示为「与创建时一致」并不等于"这个投票值得信任"。它只说明规则没被动过，不说明规则本身合理。措辞刻意只陈述事实。

## 验证

- 合约：`Poll.t.sol` 中 16 个 `test_RulesHash_*`，覆盖"静止时一致""增删改选项可见""增删白名单可见""顺序无关""重复添加无关""投票不改变指纹""不同投票指纹不同""截止时间/问题/发起人/准入方式各自被覆盖""承诺永不为零"。
- 前端：`web/test/trust.test.ts` 14 个用例，覆盖大小写、零哈希、空值、`unknown` 的措辞方向、以及 `sweepDeadline`。
- 端到端：`contracts/scripts/verify-rules-hash.ts` 在真实链上比对两个值，并以 `EXPECT=changed|unchanged` 让调用方声明预期，脚本确认或推翻。
- 浏览器：`ui-drill.ts` **独立地**从链上读取这两个指纹、自己算出结论，再要求页面得出同一个结论。只比对页面自己的文案与自己的属性将什么也证明不了——那样一个"永远显示 unchanged"的组件也会通过。

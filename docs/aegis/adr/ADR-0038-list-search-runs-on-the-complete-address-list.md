# ADR-0038 - 列表的搜索与分页在客户端进行，且"还没读到摘要"的投票必须保留

Status: `accepted`
Date: `2026-09-22`

## Source Evidence

- `web/src/lib/pagination.ts`：`parsePositiveInteger`、`clampPageSize`、`isSortOrder`、`matchesQuery`、`filterPolls`、`sortPolls`、`paginate`、`pagePolls`，以及 `ListEntry` / `entryMatches` / `sortEntries` / `pageEntries`
- `web/src/components/SearchBar.tsx`、`Pagination.tsx`、`PollList.tsx`
- `web/src/app/api/polls/route.ts`：`?page=&pageSize=&q=&sort=`
- `web/test/pagination.test.ts`：50 个测试
- 现状依据：改动前列表一次渲染全部投票，没有搜索、没有分页；`PollList` 只拿到「有摘要」的投票

## Context

列表需要搜索和分页，而这里有一个本项目特有的约束决定了实现位置：**"存在哪些投票"的唯一来源是链上的 `allPolls()`，不是索引**（ADR-0001、ADR-0011）。

于是服务端分页是做不到的。要按 `question` 排序就必须先读到每个投票的 question，也就是先读完全部投票——"只读第 2 页"根本无从表达。而按索引分页更糟：索引可能落后，一个刚创建的投票会不在任何一页里，读者看到的是"我的投票不存在"。

还有一个更隐蔽的问题。`PollList` 从链上拿到的是**地址列表**，而每个地址的摘要（question、截止时间、票数）是要**逐个**读的，读的过程中列表里会出现"有地址、还没摘要"的条目。这些条目：

- 不能因为搜索就消失。搜索是"在已知内容里找"，而这些条目的内容**还不知道**。把没有摘要的条目判为"不匹配"会让搜索结果静默地漏掉投票——而且人无法察觉漏了什么，因为漏掉的那个恰好没有可显示的内容。
- 不能随意排序。按 `most-voted` 排序时，一个票数未知的投票排在哪里都是猜的。

## Decision

**一、分页在客户端对**完整**的地址列表进行。**

服务端仍然提供 `?page=&pageSize=&q=&sort=`（`/api/polls`），因为它是给脚本用的接口而不是页面的数据源，但它内部也是先取全量再分页——`total` 是过滤后的总数，不是这一页的条数。这一点写在路由的注释里，免得后来者以为可以换成 SQL `LIMIT`。

**二、过滤 → 排序 → 分页，顺序不能换。**

`pagePolls` 是唯一入口，内部固定按这个顺序。先分页再排序会"只对这一页排序"——第 1 页看起来完全正常，第 2 页开始全错。有一个测试专门钉这个顺序。

**三、没有摘要的条目（`summary === null`）在任何查询下都保留。**

`entryMatches` 对 `summary === null` 无条件返回 `true`。这是本 ADR 里最重要的一条，理由在 Context 里：漏掉一个**看不见内容**的投票，读者无从发现。

代价是搜索"预算"时可能返回一个最终叫"午餐"的投票。这是刻意选的方向：**多显示一个不想要的，好过少显示一个存在的。**

**四、没有摘要的条目在 `newest` 下排最前，在其余排序下排最后。**

`newest` 按截止时间排序，而"刚出现在列表里"的投票按定义就是最新出现的，且读者刚创建完投票回到列表时正看向顶端。其余排序（`oldest` / `most-voted` / `question`）都是关于某个**值的陈述**，而那个值还没有——按猜测放置只是巧合而不是排序，所以统一放到末尾。

同一组内部按地址排序，保证两次请求顺序一致。

**五、页码和页大小都经过校验，非法值有明确的两条路径。**

- `parsePositiveInteger`：`null`（未提供）与非法值**都**返回 `null`，调用方各自决定默认。用 `Number` 而不是 `parseInt`，因为 `parseInt("12abc")` 是 12——一个打字错误会变成一个合法页码。
- `?sort=` 的未知值是 **400 `invalid_sort`**，不是默认成 `newest`。理由与 ADR-0036 的 `?kind=` 相同：默认会让坏链接看起来是工作的。
- `pageSize` 越界是**截断**而不是报错，且截断后的真实值回写在响应里（`pageSize`）。理由是"给我尽可能多"是合法请求，而页码越界是**钳制**到最后一页并回写 `page: pageCount`。

**六、页码的钳制结果必须回写，且 `pageCount` 最小为 1。**

空结果对应"第 1 页，共 1 页"，不是"第 1 页，共 0 页"——后者会渲染出一个不存在的页码。越界钳制会被 `clampPageSize` 式的回写暴露给调用方（`pageClamped`），而不是静默改页。

**七、排序必须是全序。**

`sortPolls` 在所有比较的末尾用 `localeCompare(address)` 兜底。没有它时，两个截止时间相同的投票可以随请求互换位置，于是**翻页的读者会看到同一个投票两次、并漏掉另一个**——这是分页和排序耦合出的错，只有全序能排除。有测试钉住。

排序比较用 `Number(endsAt)` 而不是字符串比较：`endsAt` 是十进制字符串，文本比较下 `"999999999" > "1000000000"`。

## Alternatives Considered

- **服务端分页（SQL `LIMIT`）**：被否决。"存在哪些投票"在链上，索引落后时按索引分页会隐藏刚创建的投票；而按链上分页需要先读完全部投票，也就没有省下任何工作。
- **在索引用 `LIKE '%q%'` 搜索**：被否决。同一个理由——搜索结果的完备性由索引的完整性决定，而索引明确可能落后。搜索漏掉一个存在的投票，与 ADR-0011 禁止的"谎报不存在"是同一件事。
- **没有摘要的条目判为不匹配**：被否决。这是最危险的那个选项：搜索会静默漏掉投票，且漏掉的原因（内容还没读到）恰好使读者无法察觉。
- **没有摘要的条目按"未知"排在中间**：被否决。"中间的未知"没有任何含义，且会让位置随其他投票的票数变化而漂移。
- **未知 `sort` 默认成 `newest`**：被否决。与 `?kind=` 同理，坏链接会看起来是工作的。
- **`pageSize` 越界返回 400**：被否决。"给我尽可能多"是合法意图，截断并把真实值回写更符合它。
- **用 `parseInt` 解析页码**：这是**本次差点写错**的版本，`parseInt("12abc") === 12` 会让 `?page=12abc` 静默变成合法请求。改用 `Number` 并加 `Number.isInteger` 检查，有测试钉住。

## Consequences

- 列表页的搜索和排序**完全在浏览器里**完成，因此没有网络往返，输入即响应。代价是首次渲染要读完全部投票的摘要——这本来就是旧行为，没有变差。
- 客户端搜索意味着 `/api/polls` 的搜索与页面搜索是**两份实现**。它们共用 `pagination.ts` 的纯函数，`matchesQuery` 是唯一的口径 owner；两份实现的分歧因此被限制在"谁调用它"上。
- `ListEntry` 是列表的新数据形状，被 `PollList` 使用。`PollSummary[]` 的旧形状在 `/api/polls` 保留，因为它是那个接口的既有契约。
- 搜索的匹配口径是**问题文本不区分大小写的子串**，加上**创建者地址去 `0x` 后的前缀匹配**。地址用前缀而不是子串，因为粘贴一个地址的人要的是**那个**投票，子串匹配会返回所有地址里恰好含这些字符的投票。
- `MyVotes.tsx` 的 `SCAN_LIMIT = 50` 截断**已经**向读者显示（"链上共有 N 个投票，本页只扫描了最新的 50 个"），因此本次不需要改动。

# ADR-0026 - 每个已导出的写函数都必须有调用点或一条不作调用的理由

- 状态：已接受
- 日期：2026-09-21
- 相关：ADR-0001、ADR-0009、ADR-0011、ADR-0023、ADR-0025

## 背景

`Poll` 与 `VotingFactory` 导出了一组管理写函数。它们在中止这次审计之前的状态是：

| 函数                                          | ABI 中 | `web/src` 中的调用点 |
| --------------------------------------------- | ------ | -------------------- |
| `createPoll`                                  | 是     | 1                    |
| `setWhitelist`                                | 是     | **0**                |
| `addOption` / `updateOption` / `removeOption` | 是     | **0**                |
| `startPoll`                                   | 是     | **0**                |
| `endPoll`                                     | 是     | **0**                |
| `closeAfterDeadline`                          | 是     | **0**                |
| `sweepUnclaimed`                              | 是     | **0**                |

后果不是「少了个功能」，而是**主流程不可用**：

- `Poll` 初始为 `Phase.Setup`，`vote` 在非 `Voting` 相位 revert。没有人调用 `startPoll`，所以在界面上创建的每个投票都永久停在 Setup，**一个票都投不出去**。
- 过了截止时间但仍在 `Voting` 的投票，`vote` 因 `block.timestamp >= endsAt` revert，`withdrawVote` 同样拒绝，而 `refund()` 要求 `Phase.Ended`。没有人调用 `closeAfterDeadline` 或 `endPoll`，于是**每个投票人的 0.001 ETH 押金被永久锁死**。

这两条都不是理论风险，而是「照常操作就会踩到」的状态。它们之所以没被任何测试发现，是因为**合约的每个函数都是对的**：`startPoll` 确实能把相位推到 `Voting`，`closeAfterDeadline` 确实能解锁押金。测试覆盖的是「函数是否正确」，而缺陷在于「函数是否被调用」——这是单元测试在结构上看不到的一类问题。

更麻烦的是这类缺口会**伪装成别的故障**。`vote` revert 的 `InvalidPhase(1, 0)` 在界面上表现为「无法投票」，读者会怀疑白名单、怀疑钱包、怀疑网络，而真正的原因是这个投票从未开始。

## 决策

**一、补齐所有写函数的调用点。**

新增 `web/src/components/PollAdmin.tsx`（发起人面板）覆盖 `setWhitelist`（批量）、`addOption`、`updateOption`、`removeOption`、`startPoll`、`endPoll`、`sweepUnclaimed`；`PollBallot.tsx` 接管 `closeAfterDeadline`。

**二、`closeAfterDeadline` 放在选票区，不在管理面板。**

它是**无需许可**的：合约不检查调用者身份。它因此属于任何看到「投票已过截止时间但押金取不回」的读者，而不属于发起人。放进只在 `creator === account` 时才渲染的面板里是错的——那正好在发起人已经跑路的情况下把按钮藏起来，而那正是唯一需要它的时刻。

**三、每个被禁用的控件必须渲染它被禁用的理由。**

没有任何一个 `disabled` 按钮是没有解释的。理由由 `web/src/lib/ballot-reasons.ts` 中的纯函数产生（见 ADR-0012、ADR-0027）。

**四、`setWhitelist` 在开放投票上保持可用但无效，并在合约注释中写明。**

见 ADR-0025 的代价一节。

## 理由

**为什么这值得一条 ADR，而不是当作一次普通的补功能。**

因为导致它的那种推理方式会重复。「ABI 里有这个函数」与「这个函数有人调用」是两个独立的事实，而类型检查、lint、单元测试、构建**没有一项**能连接它们：ABI 是数据，函数是代码，二者之间没有静态关系。这次是 `startPoll`，下次可能是任何新导出的写函数。

把「导出即需有调用点或理由」写下来，是为了让下一次新增写函数时，有一个明确的问题要回答：**谁调用它？** 如果答案是「前端」，那就必须真的有那个按钮；如果答案是「运维脚本」或「刻意留给未来的管理界面」，那就必须写下这句话，使它成为一个决定而不是一个遗漏。

**为什么 `closeAfterDeadline` 的放置位置是决策的一部分。**

一个无需许可的恢复函数，如果只对特权用户可见，等于不存在。此处「可见性」与「权限」必须一致：既然合约允许任何人调用，界面就不能把它关在权限门后面。这与 ADR-0009「按钮的可用性来自链而不是查询状态」是同一条原则的延伸——**界面的门必须与合约的门是同一扇门**，既不能多开也不能少开。

**为什么禁用理由必须强制存在。**

一个灰色按钮不解释自己，读者只能猜测。在这次审计中，「押金取不回」这一现象有四个完全不同的成因（未连接、相位为 Setup、交易进行中、过截止时间但未关闭），而其中只有一个是「你的钱现在真的动不了」。不写明理由，读者会用最坏的那个去理解它。详见 ADR-0012。

## 代价

- **发起人面板显著变长**：`PollAdmin.tsx` 约 800 行，涵盖六个写函数及各自的输入校验。这是必要复杂度：它对应合约上真实存在的六种管理操作，且每一种都需要「输入合法性 + 当前可用性 + 失败理由」三段。
- **地址解析必须是纯函数并单独测试**：`parseAddressList` 从组件中抽出到 `web/src/lib/admin-labels.ts`。原因很实际——`web/test/**` 无法导入 React/wagmi 组件（`ERR_MODULE_NOT_FOUND`），把逻辑留在组件里就等于放弃给它写单元测试。这不是风格偏好，而是本仓库测试基础设施的硬约束。
- **`sweepUnclaimed` 的风险仍然存在**：它断言 `totalStaked == 0` 并转账全部余额。该不变量在正常路径下成立（见下），但若未来引入任何不进 `totalStaked` 的资金流入，它会失效。本轮未改动它，仅在代码中标注了这一依赖。

## 验证

- `web/test/poll-admin.test.ts`：8 个用例覆盖 `parseAddressList`，重点是**任一地址非法即整体返回 `null`**，而不是部分成功——部分成功的批量白名单会让发起人以为所有人都加进去了。
- `web/test/ballot-reasons.test.ts`：36 个用例覆盖每个禁用理由，含一个遍历约 4000 种状态组合的扫描，断言「控件被禁用时理由永远非空」。
- `web/scripts/ui-drill.ts`：在真实浏览器中点击真实按钮，断言「每个被禁用账户都被告知原因」（`a disabled account is told why`），并在 `--vote` / `--change` / `--reject` 三种模式下驱动真实交易。
- 端到端手动验证（本轮实测）：在 `Phase.Voting` 且已过截止时间的投票上调用 `closeAfterDeadline()`，相位由 `1` 变为 `2`，索引器在下一个区块收录该 `phase_events` 行（`from_phase=1, to_phase=2`），随后 `refund()` 可正常取回押金。

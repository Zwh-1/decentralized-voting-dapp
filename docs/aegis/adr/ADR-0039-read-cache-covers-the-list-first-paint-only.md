# ADR-0039 - 读缓存覆盖列表首屏，一致性检查与健康检查永不缓存

Status: `accepted`
Date: `2026-09-22`
Amends: `docs/aegis/adr/ADR-0017-consistency-is-checked-at-one-instant.md`（把"同一瞬间"这条约束延伸到缓存边界）

## Source Evidence

- `web/src/lib/cache.ts`：`createReadCache()`，含 single-flight 与"失败不缓存"
- `web/src/lib/data.ts`：`readPollList()` / `readPollListUncached()`，`ServerState.pollList`
- `web/src/lib/config.ts`：`ServerConfig.readCacheTtlMs`，来自 `READ_CACHE_TTL_MS`，默认 2000
- `web/test/cache.test.ts`：9 个测试
- 现状依据：改动前 `getPolls()` 每次调用都完整重读——`allPolls()` 加每个投票各一次摘要读取

## Context

`getPolls()` 不是一次调用。它读 `allPolls()`，然后**对每个投票**分别读 question、截止时间、计票。所以开销随投票数增长，而列表页、投票详情页和 API 路由会在同一秒内读同一批数字。公开 RPC 既慢又限流，而**限流是被应用自己打满的**。

但本项目里缓存的代价不是"可能旧"，而是"可能与链上事实不符"——这是 ADR-0001 的核心不变量。因此问题不是"要不要缓存"，而是**哪些读取允许在哪个时间窗口内陈旧**。

有两个约束互相拉扯：

1. **一致性检查必须比较同一瞬间**（ADR-0017）。它把链上计数与索引计数对比，如果链上那一侧来自缓存，而索引是最新的，那么一个在缓存窗口内挖出的投票会**只出现在索引一侧**，检查就会报 `divergent`——缓存自己制造了一次对健康索引的错误指控。
2. **列表首屏的陈旧是被覆盖掉的**。浏览器连上钱包后会通过自己的 transport 重读同一批数据并替换它。因此服务端那一份只是**首屏**。

第 2 点是关键：这里有"陈旧值会被多久看到"的明确上界，而且它不由 TTL 决定，由"浏览器何时连上"决定。

## Decision

**一、只缓存 `getPolls()` 的结果。**

这是唯一"开销随投票数增长"的服务端读，也是唯一有浏览器侧二次读取覆盖它的读。其余读（单投票详情、计票、资格、事件）都是一次调用，缓存的收益小到不值得引入一个新的陈旧面。

**二、`checkConsistency`、`/api/health` 与计票读**永不**经过缓存。**

它们是"同一瞬间"这个性质的持有者，缓存会直接破坏它。这条写在 `cache.ts` 与 `readPollList` 的文档里，因为它是**唯一**能让缓存变错的方式，而下一次有人想"顺手也给健康检查加个缓存"时必须先读到这句话。

**三、TTL 默认 2000ms，且这个数字由确认窗口定上界。**

默认值不是"感觉够短"。上界来自 ADR-0017 的确认窗口：5 个确认、约 12 秒一个块，窗口约一分钟。2 秒远在窗口之内，所以缓存里的任何数字都不可能"在应用还称它未确认时"就已经定稿。下界由收益定：必须长到能吃掉一次页面挂载产生的重复读取。

`READ_CACHE_TTL_MS=0` 关闭缓存但**保留**并发合并。这是一个有意义的配置本身——合并突发读取，却从不返回陈旧值。

**四、single-flight 比 TTL 更重要。**

没有它，冷缓存期间 N 个并发请求会**全部**未命中并**全部**发起完整读取——缓存恰好在负载最高时不起作用。实现上就是把 producer 的 promise 在 await **之前**存进缓存条目。

**五、失败的读取永不缓存。**

这是最要紧的一条。缓存一个 rejection 会把一次瞬时 RPC 抖动变成整个 TTL 内的确定性故障，而读者会在链已经恢复很久之后仍被告知链不可达。

失败时条目被清除，且清除前会**核对身份**（`entry?.value === value`）——否则一个慢的失败读取会在一个更新的成功读取之后完成，把这个新条目误删，缓存就会在任意一次重叠之后静默失效。这个场景有专门的测试。

**六、缓存实例存在 `ServerState` 上，不在每次调用时新建。**

与 ADR-0036 里轮换 reader 的错误同源：per-call 新建会让 TTL 永远不可能达成，因为每次调用都是第一次。这一条被同一个教训钉了两次。

## Alternatives Considered

- **不用缓存，改用 viem 的 `batch` 合并请求**：被否决为**替代**方案（不是补充）。`batch` 减少往返次数但不减少读取量，而限流通常按请求数算；两者解决的不是同一个问题。作为后续优化是合理的。
- **缓存所有读，包括一致性检查**：被否决。参见 Context 第 1 点——它会制造对健康索引的错误指控，且是间歇性的、最难排查的那类。
- **用 Next.js 的 `export const revalidate` 做页面缓存**：被否决。`revalidate` 在构建期求值，无法读运行期环境变量，因此 TTL 就不能配置；更根本的是它缓存的是**整个页面的渲染结果**，会把一致性标记一起冻住，而这正是第二条禁止的。
- **默认 TTL 更长（如 30s）**：被否决。收益已经由 single-flight 拿完了，更长的 TTL 只增加陈旧面。
- **默认 TTL 为 0（只有 single-flight）**：这是一个**合理**的选项，且被认真考虑过。选择 2 秒是因为它仍在确认窗口内很远，而它带来的收益（列表页与详情页在同一秒内共享一次读取）是真实的。若运维更看重绝对新鲜，`READ_CACHE_TTL_MS=0` 就是那个开关。
- **失败时保留旧值（stale-while-error）**：被否决。ADR-0011：把"读不到"显示成"读到了旧值"，而读者无法区分。

## Consequences

- 新建投票在**服务端首屏**最多延迟 2 秒出现。浏览器连上钱包后的链上读取不受影响，因此实际可见延迟通常接近 0。
- `ServerConfig` 新增 `readCacheTtlMs`，来自 `READ_CACHE_TTL_MS`。这是纯增。
- `GET /api/polls` 的响应因此在 2 秒内可能重复。响应里**没有**声明它是缓存值——因为浏览器侧的链上读取会覆盖它，标一个"可能陈旧"的标记只会让调用方去处理一个它无法处理的差别。这是一个已知的、被接受的取舍，写在路由注释里。
- 缓存的键是"整个列表"，因此创建一个投票会**失效整份缓存**吗？不会——当前实现里创建走的是浏览器->链的路径，服务端缓存到期后自然包含新投票。这是"最终一致且窗口有界"，不是"创建后立即失效"；后者需要一个跨进程信号，代价远大于 2 秒的延迟。
